# Step 3C：计算复杂度、测量方法与内存

> 范围：3.08 复杂度指标、3.09 预算上限、3.10 测量与 RTF、3.11 ROM、3.12 RAM。本组将 184 的两条资源约束拆成五个主题。所有提案数值均不自动成为通过门槛。

> 2026-10-08 评审：已复核结论的证据范围、明确/待定状态及引用；详见[评审记录](../Review_2026-10-08.md)。依据仍是本地 2026 年 9 月材料，不推定后续会议结果。


## 1. 当前能确认的边界

[184 计算行](S4aA260184_source.md#T019-R10)要求能在标准 3GPP UE 上实现，[内存行](S4aA260184_source.md#T019-R11)提出相同的可实现性目标。指标与数值限制、RAM 是否仅计活动码率以及 data-path memory 仍有 FFS/括号。**ROM 覆盖整个 ULBC（两个码率）的 NN 参数集合**已写在无括号文字中，不能把所有两码率统计边界一概列为未定。

“标准 UE 可实现”不能直接换算成已确定的 GMAC/s、WMOPS、RTF 或 MB 门槛。C 组的核心任务是先统一计量对象，再比较预算。

## 2. 3.08：三类指标回答不同问题

| 指标 | 回答的问题 | 不能单独证明的事情 |
|---|---|---|
| MAC/s、FLOP/s | 算法需多少算术运算 | 特定芯片上的实际耗时、功耗 |
| WMOPS | 按参考算子权重计量传统 DSP/C 代码 | 与 GMAC/s 自动等价 |
| RTF | 参考平台处理耗时与音频时长之比 | 全部目标设备的部署性能 |

同样的 MAC 数量可能因算子类型、访存、并行度和 runtime 而耗时不同；相同 RTF 也可能建立在不同优化程度上。这是分析推论，不是 184 额外规定。

### 2.1 计数原则的实质分歧

[102，Samsung](S4aA260102_source.md)以 NN MAC 为主，另列传统 DSP 的 WMOPS；其 ALU/activation 超过一定比例时另报，不直接全部计入 MAC。数据移动不计 MAC。

[133，Fraunhofer](S4aA260133_source.md)提出十二条原则：C 与 ML 都计量；ONNX 是公共模型格式；C 用 G.191 STL/WMC；MAC 按 2 FLOP，ALU 和 activation 也各给 2 FLOP；数据移动不计；限制为标准 ONNX 算子；最后合为一个数值。

二者不是简单单位换算：算子范围与权重不同。133 提议 C/ML 汇总，但没有足以在本分析中冻结 WMOPS↔FLOP 的完整规范化换算规则，不能自行假定 1 WMOPS = 1 MMAC/s。

MAC=2 FLOP 只在共同认可的计数约定下使用。把 600 MMAC/s 写成 1200 MFLOP/s，需要声明这个约定，不能据此消除 ALU、activation 或 C 代码范围差异。

## 3. 3.09：上限是多个方案，不是已选数字

| 来源 | 计算量提议 | 阅读注意 |
|---|---|---|
| [115，Huawei](S4aA260115_source.md) | 约 0.6 GMAC/s | 作者设备预算分析不能直接变成统一 UE 能力 |
| [102，Samsung](S4aA260102_source.md) | 1 GMAC/s + [X] WMOPS | 两类预算分别保留，不是纯 1 GMAC/s 总上限 |
| 184 引用的早期贡献 | 2 GMAC/s | 历史方案，不作为本次已选结果 |
| [141，Orange 附件](S4aA260141_attachment_source.md#T019)、[144，Apple](S4aA260144_source.md) | 2.5 GMAC/s 方向 | 需保留各自统计口径 |
| [138，Nokia](S4aA260138_source.md) | 3 GMAC/s | 强调不同条件及对称/非对称编解码组合 |

184 注释里的 Positions 还注明需要核实；它不是投票结果。预算更高是否带来更好噪声、PLC 或音质，应由对应实验支持，不能只根据提案动机断言。

### 3.1 两个码率怎样计量

计算预算通常需要覆盖所有规定运行条件的最坏情况；不能只报最便宜运行点，也不能把互斥码率的运算机械相加。编解码若同时运行，则两方向开销都要覆盖。

ROM 更接近“支持两码率所需模型集合的并集”，共享参数计一次；RAM 则取决于哪些模块实际同时驻留。这个区别是分析框架，最终需与 184 的统计定义统一。

## 4. 3.10：静态 profiler 与 RTF 各有边界

### 4.1 132 工具能解决什么

[132，Fraunhofer](S4aA260132_source.md)提出 ONNX profiling 工具，报告 ML 运算、参数及模型大小，并对比工具输出。它有助于自动实现统一计数规则，但工具自身不能决定哪些算子应计、权重多少、C 代码是否已覆盖。

评测应固定工具版本、ONNX opset、输入形状、调用次数和计数规则。若一个模型每帧调用多次，仅模型一次 inference 的 MAC 不是整个 codec 的每秒计算量。

### 4.2 RTF 路线

[095，Spreadtrum/China Telecom](S4aA260095_source.md)主张以 RTF 为主要指标，统一参考 CPU 和执行环境；统计各线程 CPU 时间，排除操作系统暂停调度时间，并覆盖实际触发的 PLC/恢复处理。

[160，Lenovo](S4aA260160_source.md)提出 Raspberry Pi 5、单线程 ONNX CPU 路线和统一软件环境；同时报告静态计数及动态内存。两份提案并不天然给出同一个已冻结的 benchmark。

按 160 的方向，可写为 `RTF = (encoder time + decoder time) / 对应音频时长`。用 40 ms 音频作分母，耗时 8+12 ms 时 RTF=0.5；这是说明公式的例子，不是候选实测结果。

RTF<1 说明该测量环境下统计耗时低于音频时长，但不能独自保证共享 CPU、突发 PLC、尾部延迟和持续热负载下都能按时完成。平均值、P50/P99、最大值及测量条件需要一起报告。组合耗时的 P99 不能直接用 encoder P99 + decoder P99 代替。

## 5. 3.11：ROM 不是只看参数数量

184 讨论总 ROM 覆盖两码率，NN 参数上限、字节数和精度未定。对于 N 个参数：

| 假设 | 3M 参数 | 6M 参数 |
|---|---:|---:|
| 每参数 2 byte | 6 MB | 12 MB |
| 每参数 4 byte | 12 MB | 24 MB |

这里用十进制 MB，仅计权重；不包含程序、表格、runtime、量化元数据。实际提交必须声明是否包含这些内容，MB/MiB 也需统一。

[139，Nokia](S4aA260139_source.md)提出 7.5M 参数方向，并建议以参数数和字节数的 tuple 报告。[115](S4aA260115_source.md)提出 6M/12MB、2 byte 口径，但摘要表的 RAM 标记与正文 ROM 描述存在不一致，需要核对，不能默默修成已定 RAM 上限。

141 附件明确提出 3M、float32（对应仅权重约 12 MB），而 184 的 ROM/RAM 候选清单含问号归属。应优先引用附件实际文字，不能把主干待核实清单当作作者已澄清的最终立场。

144 对约 5M 参数的表述是推荐/预期范围，并以计算上限为约束；不能把该建议直接解释为与 GMAC 上限独立的已冻结硬限制。184 列出 5M 方案时仍处于待核实的候选清单中。

## 6. 3.12：RAM 还包括运行时状态与中间结果

[154，Qualcomm](S4aA260154_source.md)区分覆盖全部码率的 ROM 与只按当前活动码率统计的 RAM。[133](S4aA260133_source.md)考虑压缩权重被转换为 FP32 的推理情况；参数加载本身就可能占用 RAM。

RAM 还可能包括 activation、缓存状态、scratch buffer、音频帧/包缓冲和 runtime 工作区。184 对 data-path memory 尚未定，因此“5M 参数”不等于“全部 RAM 只有 20 MB”。

[160](S4aA260160_source.md)建议动态 RAM 的均值、P50、标准差、最大值等报告。对部署可实现性，峰值和驻留对象比单独均值更有解释力；是否计 OS/runtime 基础开销应统一。

184 的 RAM 清单还列出 3M、5M、6M、12M 参数及含 state 的 12.5 MB 等候选值，其中部分作者归属带问号。这些口径不同，不能作为同一数轴上可直接替换的门槛；须先固定精度、状态和 data-path 的包含范围。

“仅当前活动码率”还需解释双向不同码率或模式过渡时的同时驻留情况。这是与 138 的非对称运行讨论相关的待澄清项，不是当前已要求支持任意切换。

## 7. 建议形成的候选报告

| 项目 | 最少需写清楚的内容 |
|---|---|
| 运行条件 | 码率、采样接口、带宽、帧长、bundle、DTX、丢包模式 |
| 静态计算 | NN 各类操作、C/WMOPS、调用次数、最坏条件 |
| ROM | 参数并集、精度、字节数、共享计数、程序/runtime 边界 |
| RAM | 活动模型、状态、activation、buffer、峰值及计量边界 |
| RTF | 平台、runtime、线程、CPU 时间/墙钟时间定义、统计分布 |

该表是分析建议，不替代未来 ULBC-7/8 合规表。当前应先定“怎么量”，再定“多少算通过”。
